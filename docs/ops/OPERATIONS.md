# 運営の実務(MVP の想定運用)

「システムがやること」と「人がやること」の線引き。
別紙1 第3項で対象外にした機能(売上金の送金・返金 API・配送業者連携)は、
**運営の手作業で埋める**前提になっている。その手順をここに書く。

障害が起きたときの一次対応は [RUNBOOK.md](RUNBOOK.md)。

---

## お金の流れ

```
購入者 ──(カード決済)──> Stripe ──> 運営の Stripe アカウント(全額)
                                              │
                                    (運営が手で振込)
                                              ▼
                                          出品者の口座
```

**入金は全額いったん運営に入る。** Stripe Connect を使っていないため、
出品者への支払いは運営からの振込になる。手数料(既定 7%)の差引も手計算。

商品代金 100,000 円の取引なら、

|                     | 金額                                              |
| ------------------- | ------------------------------------------------- |
| 購入者の支払い      | 100,000 円 → Stripe 経由で運営へ                  |
| Stripe の決済手数料 | Stripe 側の料率(運営負担。国内カードで 3.6% 前後) |
| CycleX の手数料     | 7,000 円(運営の収益)                              |
| **出品者への振込**  | **93,000 円**(運営が手で振込)                     |

出品画面に出る「受取額の目安」はこの 93,000 円のこと。**表示だけ**で、
振込の実行や記録はシステムの外にある。

## 日次(5 分)

管理画面を上から順に見る。異常がなければ何もしない。

| #   | 見る場所                              | 何をするか                                 |
| --- | ------------------------------------- | ------------------------------------------ |
| 1   | `/admin`                              | 会員数・出品数・成立取引・GMV の推移を確認 |
| 2   | `/admin/reports`                      | 未対応の通報に対応(下記)                   |
| 3   | `/admin/transactions?refund=pending`  | **要返金**。空でなければ返金作業(下記)     |
| 4   | `/admin/transactions?stale=paid7`     | 支払い後 7 日たっても発送されていない取引  |
| 5   | `/admin/transactions?stale=shipped14` | 発送後 14 日たっても受取確認がない取引     |
| 6   | Sentry / Vercel のログ                | エラーが溜まっていないか                   |

4 と 5 は催促メールが日次バッチから自動で飛ぶので、**基本は放置でよい**。
それでも動かない取引だけ、メッセージで当事者に声をかける。

### 日次バッチが自動でやること

毎日 04:00(JST)に `/api/cron/daily` が動く。人の操作は要らない。

1. 評価の自動公開(14 日経過)
2. 未決済取引の掃除(90 分以上 `pending_payment` のものをキャンセルし、商品を戻す)
3. 取引と商品の状態ズレの検出(見つけたら警告を出すだけ。直さない)
4. 保存されなかった画像の回収
5. 停滞取引の催促メール
6. レート制限の記録の掃除

1 回あたり各処理 300 件までで、超えた分は翌日に回る。

## 週次(30 分〜1 時間)

### 出品者への振込

**ここが MVP でいちばん手間のかかるところ。**

1. `/admin/transactions?status=completed&from=YYYY-MM-DD&to=YYYY-MM-DD` で
   期間中に完了した取引を出す
2. 出品者ごとに商品代金を合計し、手数料 7% を引く
3. Stripe の残高から出金し、出品者の口座へ振込
4. **振込済みかどうかを記録する場所がシステムにない。**
   表計算などで台帳を作り、取引 ID・出品者・金額・振込日を管理する

> **注意**: 管理画面には「振込済み」の印を付ける機能がなく、CSV 出力もない。
> 同じ取引に二重に振り込む・振り込み漏れが出る、という事故は**台帳の運用でしか防げない**。
> 取引件数が増えたら Stripe Connect の導入(契約変更)を検討したほうがよい。

出品者の口座情報を集める画面も無いので、**初回の振込時にメッセージか
問い合わせ窓口で聞く**運用になる。

## 随時

### 通報への対応

`/admin/reports` に一覧が出る。通報の理由と対象(出品 / 会員 / メッセージ)を見て、

| 判断           | 操作                                                                             |
| -------------- | -------------------------------------------------------------------------------- |
| 問題あり(出品) | 出品詳細から**非表示にする**。理由は出品者にだけ見える                           |
| 問題あり(会員) | 会員詳細から**利用停止**。停止するとセッションも失効し、全ページから閉め出される |
| 問題なし       | 通報を**対応済みにする**(何もしないで閉じる)                                     |

出品を非表示にすると、商品画像は非公開のバケットへ退避される。
公開 URL を知っている人にも見えなくなる。

### 返金

**返金 API は実装していない。Stripe ダッシュボードでの手作業。**

返金が必要になるのは主に 2 つ。

1. **キャンセル後に入金が確定した**(コンビニ払いなどの後払いで起きる)
   → `/admin/transactions?refund=pending` に出る。購入者にも自動で
   「返金します」のメールが飛んでいる
2. **進行中の取引を返金した**(運営判断)
   → Sentry と運営へのメールで通知が来る。取引は自動では止まらない

手順:

1. Stripe ダッシュボードで該当の PaymentIntent を返金する
2. 管理画面の取引詳細で「返金済みにする」を押して消し込む
   - Stripe の `charge.refunded` Webhook が届けば自動で消える。
     届かない・一部返金のときだけ手で押す

### 止まってしまった取引

| 状況                            | 操作                                                        |
| ------------------------------- | ----------------------------------------------------------- |
| 支払い前のまま動かない          | **強制キャンセル**(履歴に `canceled_without_expire` が残る) |
| 発送されない / 受取確認されない | 当事者に連絡。どうしても動かなければ状態を**強制遷移**      |
| 状態ズレの警告が出た            | 取引の状態を正として、商品側を手で合わせる                  |

強制操作はすべて監査ログ(`admin_audit_logs`)に残る。

### 配送について

**配送業者との連携はない。** 実務上はこうなる。

|                | 誰が               | どうやって                                                         |
| -------------- | ------------------ | ------------------------------------------------------------------ |
| 住所の受け渡し | 購入者             | 支払い後、**メッセージで出品者へ送る**(住所入力フォームは無い)     |
| 送り状         | 出品者             | 自分で用意(コンビニ・営業所・各社のアプリ)                         |
| 送料           | 出品時の選択による | 送料込み(出品者負担) / 着払い(購入者が受取時に業者へ支払う) / 対面 |
| 追跡番号       | 出品者             | 発送連絡の**自由記入欄**に書く。システムは中身を見ていない         |
| 到着の確認     | 購入者             | 取引画面で「受け取りました」を押す                                 |

支払い後、購入者の取引画面には「お届け先をお伝えください」という案内が出る。
住所を集める画面が無いため、これが無いと双方が待ち続けて取引が止まる。

## 月次

- 手数料収入の集計(Stripe の残高推移と週次の台帳を突き合わせる)
- ブランドマスタの手入れ(`/admin/brands`。出品者の自由入力から拾って正規化する)
- バックアップの確認(Supabase の PITR、または `pg_dump` の保存)

## 人員の目安

| 業務           | 頻度   | 時間                       |
| -------------- | ------ | -------------------------- |
| 管理画面の確認 | 毎日   | 5 分                       |
| 通報対応       | 発生時 | 1 件 5〜10 分              |
| 返金           | 発生時 | 1 件 10 分                 |
| 振込           | 週次   | 取引 20 件で 30 分〜1 時間 |
| 問い合わせ対応 | 随時   | 件数による                 |

**取引が月 100 件を超えたあたりから振込作業が回らなくなる。**
そこが Stripe Connect を入れる判断のめどになる。

## 対象外のまま運用するリスク

正直に書いておく。

| 項目             | 何が起きうるか                                  | いまの防ぎ方                             |
| ---------------- | ----------------------------------------------- | ---------------------------------------- |
| 送金が手作業     | 二重振込・振込漏れ                              | 台帳の運用のみ。システム側の歯止めは無い |
| 返金が手作業     | 返金忘れで購入者の代金が滞留                    | `?refund=pending` を毎日見る             |
| 配送追跡が無い   | 「送った / 届いていない」の紛争で判断材料が無い | 発送連絡の自由記入とメッセージの履歴     |
| 本人確認が無い   | 盗難車の出品、なりすまし                        | 通報を受けてからの事後対応               |
| エスクローが無い | 受取前に出品者へ振り込むと回収できない          | **取引完了後にのみ振込**(運用で守る)     |

最後の 1 行は守り方を間違えると損失が出る。**`completed` になった取引だけを
振込の対象にする**こと。`paid` や `shipped` の段階で振り込まない。

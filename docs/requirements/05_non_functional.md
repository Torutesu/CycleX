# 05. 非機能要件

MVP(事業検証)として妥当な水準に限定する。負荷試験・脆弱性診断・セキュリティ監査・アクセシビリティ対応・リリース後の運用/監視は対象外(別紙1 第3項)。

## 1. 対応環境

| 項目 | 要件 |
|---|---|
| ブラウザ | 開発時点の最新版 Chrome / Safari / Edge。モバイルは iOS Safari・Android Chrome の最新版 |
| 画面幅 | 320px〜1920px で表示崩れがないこと。設計基準はモバイル 375px(スマホファースト)、PC は最大コンテンツ幅 1280px |
| OS | 上記ブラウザが動作する iOS / Android / Windows / macOS |

## 2. 性能(目標値)

| 項目 | 目標 |
|---|---|
| 主要ページ(ホーム・検索・商品詳細)の表示 | 通常回線で概ね 3 秒以内に主要コンテンツ表示(SSR + 画像遅延読み込み) |
| API 応答 | 通常時 1 秒以内(検索含む) |
| 想定規模 | 検証期間中: 会員 〜1,000、出品 〜5,000、同時アクセス 〜50 程度。この規模で体感遅延がないこと(負荷試験は実施しない) |
| 画像 | アップロード時にリサイズ・サムネイル生成し、一覧はサムネイルのみ配信 |

## 3. 可用性・データ保全

- ホスティング/DB はマネージドサービス(Vercel / Supabase)の標準 SLA に準拠し、独自の冗長化は行わない
- DB バックアップは Supabase の自動バックアップ(日次)を利用
- 稼働率の保証、監視・アラート体制の構築は対象外

## 4. セキュリティ

- 全通信 HTTPS(TLS)
- パスワードはハッシュ保存(Supabase Auth 標準)、カード情報は非保持(Stripe に委譲)
- 認可は RLS+サーバー検証の二重化([04_tech_stack.md](04_tech_stack.md) §5)
- 管理画面は管理者ロールのみアクセス可
- 個人情報(メールアドレス等)は画面上、本人・管理者以外に表示しない

## 5. 保守性・移行性

- TypeScript strict、ESLint/Prettier による静的検査を CI で必須化
- DB スキーマはマイグレーションファイルで管理(再現可能な環境構築)
- 環境依存値はすべて環境変数化し、`.env.example` を整備
- README にローカル環境構築手順・デプロイ手順を記載

## 6. ログ・データ

- 取引ステータス変更は transaction_events に操作者付きで記録(監査証跡)
- メール送信結果は email_logs に記録
- アプリケーションログは Vercel / Supabase の標準ログに準拠(独自ログ基盤・アクセス解析は対象外)

## 7. 運用引き継ぎ(納品時)

- 管理者アカウントの発行手順、Stripe / Supabase / Resend / Google OAuth の設定項目一覧を README に記載
- リリース後の運用・監視・保守は対象外のため、体制構築は甲側で実施

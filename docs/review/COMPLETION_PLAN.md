## 1. 直ちに直すべき欠陥(Phase A)

裏取り済み。番号は §4 の計画と対応する。

### A-1【致命】キャンセル済み取引に入金が完了しても、支払いが黙って捨てられる

- `src/features/transaction/webhook-rules.ts:37-39` — 取引が `pending_payment` 以外なら `skip`。`canceled` に `payment_status=paid` が届いても何も記録しない
- リポジトリ内に `stripe.checkout.sessions.expire` の呼び出しが **存在しない**。DB 側でキャンセルしても Stripe の決済画面は 45 分間生きたまま
- 発生経路:
  1. 管理者が `pending_payment` をキャンセル(`admin/rules.ts:85-87` の `isCancellable` は pending を含む)→ 購入者はそのまま支払える
  2. Webhook 障害が 90 分を超える → 日次バッチ `cleanupStalePendingTransactions` がキャンセル → Stripe は最大 3 日再送する
  3. 商品は pending 中も `published` のままなので、キャンセル後に**別の購入者が同じ商品を買え、二重販売**になる
- いずれも `paid_at` が付かないので管理画面の「要返金」にも出ない
- 修正:
  - `pending_payment` をキャンセルする全経路(管理者キャンセル・日次バッチ・購入者本人の再購入)で、先に `sessions.expire()` を呼ぶ。API がエラー(既に完了)なら `sessions.retrieve()` で `payment_status` を確認し、`paid` なら `paid` へ遷移させる
  - `decideCompleted` に「pending 以外 かつ paid かつ `stripe_payment_intent_id` 未記録」の分岐 `late_payment` を追加。`paid_at` / `payment_intent` を記録し `transaction_events` に残し、管理者へメール。`needsRefund` はこれで true になる
  - `webhook-rules.test.ts:30-32` は現状の skip を正として固定しているため更新する

### A-2【致命】Webhook が DB の一時障害を「不正イベント」として 200 で握りつぶす

- `src/features/transaction/service.ts:73-77` `getTransaction` は `error` を見ず `null` を返す → `decideCompleted` が `invalid` → `route.ts:36-38` はログだけ出して **200**。Stripe は 2xx を受けると再送しない
- 結果: 入金済みなのに取引は `pending_payment` のまま → 90 分後にバッチがキャンセル → `paid_at` 無しで「要返金」にも出ない
- 修正: `getTransaction` は `error` を throw。「metadata はあるが取引が無い」は 500 を返して再送させ、真に不正(metadata 無し)だけ 200 にする

### A-3【致命】本番でデモ決済が有効になりうる

- `src/lib/demo.ts:18-20` — `ALLOW_DEMO_CHECKOUT=1` かつ `STRIPE_SECRET_KEY` 未設定で有効。Preview の env をコピーした/本番でキー登録を忘れた組み合わせで、**実ユーザーが無料で「支払い済み」を作れる**
- 修正: `VERCEL_ENV === "production"` ではデモを無効化し、Stripe キー未設定なら `startPurchase` を失敗させる。あわせて `RESEND_API_KEY` 未設定時に `email_logs.status='sent'` で記録している件(`send.ts:56-61`)を `failed`(または `skipped`)に変え、本番では起動時に必須 env を検証する

### A-4【高】`next` パラメータにタブ文字を含めるとオープンリダイレクト

- `src/lib/utils.ts:88-94` `safeRedirectPath` は `/%09/evil.com`(デコード後 `"/\t/evil.com"`)を通す。`login/page.tsx:36 redirect(next)` と Server Action の `redirect()` の両方で外部へ遷移する(Node で `new URL("/\t/evil.com", base).href === "https://evil.com/"` を確認済み)
- 修正: 制御文字・空白を含む値を拒否し、`new URL(next, "http://local.invalid")` で origin が変わらないことを検証。`/login` `/auth/*` へのループも弾く。`utils.test.ts` にケース追加

### A-5【高】利用停止しても Supabase Auth のセッションが生きている

- `src/features/admin/actions.ts:73-78` `suspendUser` は `users.status` を更新するだけ。退会(`auth/actions.ts:310`)は BAN しているのに停止はしていない
- 停止後も本人 JWT で PostgREST / Storage を直接叩ける: スレッド・取引の SELECT、`display_name` 等の UPDATE(`harden_grants.sql:37`)、favorites、画像アップロード(`storage.sql:19-25` は `auth.uid()` のみ)
- さらに `lib/supabase/proxy.ts:74` は会員パスと `/admin` でしか status を見ないため、停止中でも `/` `/search` `/items/*` がログイン状態で描画される(要件「停止画面のみ表示」未達)
- 修正: 停止時 `ban_duration: "876000h"` + `app_metadata.status='suspended'`、解除時に戻す。proxy は `app_metadata.status` を見て全パスで `/suspended` へ(DB 往復不要)。書き込み系 RLS に `status='active'` 条件を追加

### A-6【高】管理ページの認可がレイアウトと proxy にしか無い

- `src/app/admin/*/page.tsx` は `requireAdmin()` を呼ばず service role の `features/admin/queries.ts` を直接使う。Next 16 のドキュメントが明示的に非推奨とするパターン(レイアウトはナビゲーション時に再実行されない)
- 今日時点で到達可能な穴は無いが、ルートを 1 つ足すだけで崩れる構造
- 修正: `features/admin/queries.ts` の各関数冒頭で `await requireAdmin()`(`getCurrentUser` は `cache()` 済みなので追加コスト無し)

### A-7【高】出品フォームの端末控えに `id` が混入し、公開済み商品を上書きする

- `listing-form.tsx:121` `backupEnabled = !defaults.id` は `defaults` を見ているため、下書き保存で `set("id")` した後(`:192`)も控えの保存が続く。`clear()` 直後に `{...values, id}` が `cyclex:listing-draft:new` に書き戻される
- 後日 `/sell` を開く → 「前回の内容が残っています」→ 復元 → 別の自転車を入力して公開 → `values.id` が旧商品を指し、`upsertListing` の update 分岐(`actions.ts:144-172`)で**公開済み商品が上書き・画像差し替え**される
- キーが `"new"` 固定で**ユーザー間でも共有**される(共有端末で他人の入力内容が提示され、他人の画像パスが混入して公開に失敗する)
- 修正: 控えから `id` を除外、`backupEnabled = !defaults.id && !values.id`、キーに `userId` を含め、ログアウト時に削除

### A-8【高】退会後に同一メールで再登録できない(FR-01-5 違反)

- `auth/actions.ts:310` は auth.users を BAN するだけで行を残す。同メールで `signUp` すると Supabase は偽の成功を返し確認メールは来ない。Google 再ログインは `user_banned` → 「リンクの有効期限が切れています」と誤表示(`callback-rules.ts:39`)
- 修正: メールを `withdrawn+{id}@invalid.local` へ付け替え(トリガーで `public.users.email` も同期される)、service role の RPC で `auth.identities` を削除。`callback-rules` に `user_banned` の分岐を追加

### A-9【中】プロフィール列を PostgREST 直叩きで無検証に更新できる

- `harden_grants.sql:37-38` で `display_name / avatar_url / bio / prefecture / notification_prefs` の UPDATE を許可しているが DB に CHECK が無い
- `avatar_url` に外部 URL を入れると `images.ts:30` がそのまま返し、`next/image` が未許可ホストで**例外**を投げて、その出品者の商品詳細・プロフィール・メッセージ一覧が全員に対して `error.tsx` に落ちる
- 修正: `display_name` 1〜30、`bio` ≤1000、`prefecture` `01`〜`47`、`avatar_url` は `{id}/...` か `*.googleusercontent.com` のみ、`notification_prefs` は object かつ 1KB 未満、の CHECK を追加。`next.config.ts` の Google ホストを `*.googleusercontent.com` に

### A-10【高・運用】本番を誤って壊せる導線がドキュメントとスクリプトにある

- `docs/DEPLOY.md` §3 が「`.env.local` を本番値に書き換えてシードを実行」と案内。`scripts/seed-users.mjs:17` は**管理者 `admin@cyclex.test` をパスワード `パスワード123`** で作る(公開リポジトリに載った既知パスワード)。`seed-refresh.mjs` は全出品を書き換え、`seed-images.mjs --replace` は画像行を削除する

- `.mcp.json` に本番 `project_ref` と書き込み可能な features がコミットされている
- 修正: 全スクリプト・E2E に「URL が `127.0.0.1`/`localhost` 以外なら明示フラグ無しで終了」するガード。DEPLOY.md から本番シード手順を削除。`.mcp.json` は `read_only=true` にするか gitignore
